# JSON over SPI between two ESP32-POE-ISO boards (UEXT1)

Two Olimex ESP32-POE-ISO boards connected through their UEXT1 connectors:

- **Server** is the SPI master. It sends a snapshot of all the `openami/StreetEMS_A779A8/meter_*` MQTT topics (one JSON object of about 5.1 KB) as fast as the client can take it.
- **Client** is the SPI slave. It keeps a receive buffer queued, tells the server it is ready on a handshake line, and checks that each frame matches the snapshot byte for byte.

SPI is full duplex, so on every transaction the client also sends a header-only **ack** frame back on MISO, and the server checks it.

By default each board prints one summary line per 100 transactions, with the success count and throughput. A build flag (`VERBOSE_LOG=1`) brings back the full per-transaction trace, which shows CS edges, hex dumps and the JSON.

Both roles are built from the same `src/main.cpp`. A build flag picks the role (`-DROLE_SERVER` or `-DROLE_CLIENT`), and `platformio.ini` defines one environment for each.

### The payload

For now the JSON is hardcoded in `include/meter_snapshot.h`. That file is generated by `tools/snapshot_meters.py`, which connects to `public.cloud.shiftr.io` (user `public`, password `public`), collects the retained `openami/StreetEMS_A779A8/meter_*` messages, and embeds each payload verbatim:

```json
{"meter_0":{"timestamp":374363,"meter_id":0,"phase":1,"phase_label":"A",...,"THD_V":0},
 "meter_1":{...}, ..., "meter_5":{...}}
```

To refresh it:

```sh
pip install paho-mqtt
python3 tools/snapshot_meters.py      # rewrites include/meter_snapshot.h, then rebuild both boards
```

The header comment records when the snapshot was taken, which topics it contains, and its size. The capture on 2026-09-25 had 6 topics and 5098 bytes. Both boards compile the same header: the server sends it, and the client compares against it.

**Room to grow:** frames are variable length (see §3), and both boards size their buffers for `MAX_FRAME_SIZE` (16 KB by default). The JSON can grow to 16372 bytes, about 3× the current size, with no code changes. A larger JSON only costs proportionally more wire time. If it outgrows that limit, the build fails with a `static_assert`. Raise `MAX_FRAME_SIZE` (up to 65536, the limit of the 16-bit length field) and rebuild both boards.

## 1. Wiring

### UEXT1 pinout on the ESP32-POE-ISO

UEXT is a 2×5, 0.1" boxed header. Pin 1 is marked with a triangle or square pad.

```
        UEXT1 (looking at the header)
      ┌───────────────────────────┐
      │  1 3V3     2 GND          │
      │  3 GPIO4   4 GPIO36       │
      │  5 GPIO16  6 GPIO13       │
      │  7 GPIO15  8 GPIO2        │
      │  9 GPIO14 10 GPIO5        │
      └───────────────────────────┘
```

| UEXT pin | GPIO   | UEXT name | Used here as           | Server (master)  | Client (slave)   |
|---------:|--------|-----------|------------------------|------------------|------------------|
| 1        | 3.3 V  | 3V3       | **do not connect**     | –                | –                |
| 2        | GND    | GND       | common ground          | GND              | GND              |
| 3        | GPIO4  | TXD1      | handshake ("ready")    | input            | output           |
| 4        | GPIO36 | RXD1      | unused                 | –                | –                |
| 5        | GPIO16 | SCL       | unused                 | –                | –                |
| 6        | GPIO13 | SDA       | unused                 | –                | –                |
| 7        | GPIO15 | MISO      | MISO                   | input            | output           |
| 8        | GPIO2  | MOSI      | MOSI                   | output           | input            |
| 9        | GPIO14 | SCK       | SCK                    | output           | input            |
| 10       | GPIO5  | SSEL      | CS (active low)        | output           | input            |

These match `MISO/MOSI/SCK/SS/TX1` in PlatformIO's `esp32-poe-iso` board variant. If your board revision is different, check it against the Olimex schematic. Every pin can be overridden with a `-DPIN_xxx=` build flag.

### Jumper connections (6 wires, pin-to-pin)

SPI lines connect **straight through**. Unlike UART TX/RX, they do not cross: MOSI goes to MOSI and MISO goes to MISO. The names describe the master's and slave's roles, not the direction on each board.

```
   SERVER UEXT1                          CLIENT UEXT1
   ────────────                          ────────────
   pin  2  GND   ─────────────────────── pin  2  GND
   pin  3  GPIO4 ◄────── handshake ───── pin  3  GPIO4
   pin  7  MISO  ◄────── MISO ────────── pin  7  MISO
   pin  8  MOSI  ─────── MOSI ─────────► pin  8  MOSI
   pin  9  SCK   ─────── SCK ──────────► pin  9  SCK
   pin 10  CS    ─────── CS ───────────► pin 10  CS

   pin  1  3V3      (leave unconnected on both boards)
```

Use short female-female Dupont wires (under about 15 cm), all the same length if you can. Connect **GND first** and disconnect it last.

**Using a 10-pin ribbon (UEXT-to-UEXT) cable:** a straight IDC ribbon also connects pins 1 to 1 and 2 to 2 through 10 to 10, so it would work. However, it ties the two boards' 3.3 V rails together, which puts the two regulators in parallel and can back-power a board that is switched off. Cut or lift the pin 1 conductor if you use a ribbon. The other extra pins (4, 5, 6) are only inputs or unused here, so connecting them does no harm.

## 2. Build, flash, monitor

```sh
pio run -e server -t upload --upload-port /dev/cu.usbserial-AAAA
pio run -e client -t upload --upload-port /dev/cu.usbserial-BBBB

pio device monitor -e server -p /dev/cu.usbserial-AAAA
pio device monitor -e client -p /dev/cu.usbserial-BBBB    # in a second terminal
```

Tunables are set in `[env] build_flags` in `platformio.ini`. Both boards **must** use the same value for all of them:

| Flag                 | Default  | Meaning |
|----------------------|----------|---------|
| `SPI_CLOCK_HZ`       | 8000000  | SCK frequency. The master uses the nearest 80 MHz / n at or below it: 8, 8.9, 10, 11.4, 13.3, 16, 20, 26.7 MHz… The actual value is printed at boot. |
| `SPI_INPUT_DELAY_NS` | 75       | Server only: the ESP32 slave's MISO output delay through the GPIO matrix. Used for the MISO timing warning (see caveat 9). |
| `SPI_MODE_NUM`       | 1        | SPI mode (CPOL/CPHA). Mode 1 or 3 is recommended with the slave's DMA (see caveats). |
| `MAX_FRAME_SIZE`     | 16384    | Largest frame either board can handle. Multiple of 4. The JSON can be up to this minus 12 bytes. |
| `USE_HANDSHAKE`      | 1        | Use the UEXT pin 3 ready line |
| `SEND_INTERVAL_US`   | 0        | Time between server transactions. 0 = back to back, as fast as the client can keep up. |
| `HANDSHAKE_TIMEOUT_US` | 10000  | How long the server waits for the ready line before it counts the transaction as FAIL |
| `REPORT_EVERY`       | 100      | Transactions per summary line |
| `VERBOSE_LOG`        | 0        | 1 = full per-transaction trace. Also set `SEND_INTERVAL_US=1000000`, because the trace can't keep up otherwise. |
| `HEXDUMP_BYTES`      | 32       | Verbose mode only: raw bytes printed per frame (0 turns the hex dump off) |

### Expected serial output (default)

At boot the server prints the clock it actually got and the MISO timing limit:

```
clock: requested 8000000 Hz, actual 8000 kHz; full-duplex MISO limit for 75 ns input delay: 8888 kHz
```

After that, each board prints one line per `REPORT_EVERY` transactions. The line ends in `OK` if all of them were good, and otherwise gives the count of each. The rates count JSON payload bytes from successful transactions only:

```
[SERVER] #1200 OK  188 tx/s  960 kB/s
[SERVER] #1300 OK:97 FAIL:3  183 tx/s  910 kB/s
```
```
[CLIENT] #1200 OK  188 tx/s  960 kB/s
```

These are **estimates, not measurements**. The frame is 5112 bytes on the wire, which takes about 5.1 ms at 8 MHz, plus about 0.2 ms for the client to check the frame and re-queue. That gives roughly 185–190 transactions a second, or about 950 kB/s of JSON. See caveat 18 for going faster.

What counts as a success:

| Board  | OK means | FAIL means |
|--------|----------|------------|
| Server | The handshake came within `HANDSHAKE_TIMEOUT_US`, and the ack on MISO is a valid `'A'` frame (magic and CRC correct, no payload) | Handshake timeout (client absent or too slow), a bad or missing ack, or an SPI driver error |
| Client | The frame received on MOSI is a valid `'D'` frame whose payload is exactly the hardcoded snapshot | Bad magic or CRC, a truncated transfer (CS released early), or a payload that differs from the snapshot |

The counts don't have to match between boards. A handshake timeout counts as FAIL on the server, but the client never sees that transaction, so it doesn't count it at all. Each side's `#` is its own transaction counter.

Server:

```

```

Right after either board boots, the first block may show a few FAILs. This is expected, because the other board wasn't ready yet.

## 3. Control flow

### Why a handshake line?

An SPI slave can't delay the master. If the server clocks data while the client has no buffer loaded in the SPI peripheral, those bits are **lost without any error**. On the ESP32 slave, a buffer is loaded only while a transaction is queued with `spi_slave_queue_trans()`. Between transactions the client is busy checking the frame and re-queuing. The handshake line tells the server when it is safe to clock.

### One transaction, step by step

```
 SERVER (master)                                   CLIENT (slave)
 ───────────────                                   ──────────────
 setup: build DATA frame once                      write ACK header into txBuf
        (snapshot JSON, padded to 4 bytes)         spi_slave_queue_trans(tx, rx, MAX_FRAME_SIZE)
                                                   post_setup_cb ISR: HS -> HIGH
 seq++ (patch header)
 wait for HS == HIGH (timeout 10 ms) ◄──────────── HS HIGH
 CS -> LOW   ─────────────────────────────────────► CS falling edge (logged via GPIO ISR)
 delay 2 us
 spi_device_polling_transmit(5112 bytes, DMA)
   SCK  ─────────────────────────────────────────► shifts MOSI into rxBuf (DMA)
   MOSI ─── DATA frame: meter snapshot JSON ─────►
   MISO ◄── ACK header (then zeros) ──────────────  shifts txBuf out
 delay 1 us
 CS -> HIGH  ─────────────────────────────────────► CS rising edge = end of transaction
                                                   post_trans_cb ISR: HS -> LOW
 wait for HS == LOW (≤1 ms) ◄──────────────────────
 check ACK frame, tally                            spi_slave_get_trans_result() returns
 loop immediately (SEND_INTERVAL_US=0)             trans_len = bytes actually clocked
                                                   check CRC + compare to snapshot, tally
                                                   loop: re-queue (HS HIGH again)
```

Details:

- **The server uses the ESP-IDF `spi_master` driver with DMA**, not Arduino's `SPIClass`. `SPIClass` moves data through the 64-byte FIFO with the CPU, which leaves gaps and costs CPU time on a 5 KB frame. The server holds the bus permanently (`spi_device_acquire_bus`) and uses polling transmit to keep per-transaction overhead low.
- **The server controls CS manually** with `gpio_set_level`. The hardware CS is not used, so each assert and deassert can be logged.
- **The server waits for HS to drop after each transaction.** Back to back, it would otherwise check the handshake again before the client's `post_trans_cb` had lowered it. It would see the old HIGH and clock into a slave with nothing queued.
- **The client doesn't control CS**, because the slave peripheral watches it. The client also attaches a GPIO `CHANGE` interrupt to the same pin. The ISR only stores a timestamp and pin level in a ring buffer. In verbose mode the main loop prints those entries, since you can't `Serial.print` from an ISR.
- **The ack always lags by one transaction.** The MISO data has to be in `txBuf` before the master starts clocking. So the ack sent during transaction *N* carries the last seq the client received *before* *N*.
- **Frames are variable length.** The slave always queues a `MAX_FRAME_SIZE` buffer, because it can't know the length in advance. The master clocks only header + JSON, rounded up to a multiple of 4. The slave reads the actual count from `trans_len`. So the snapshot costs 5112 bytes of wire time, not 16 KB, and it can grow without any configuration change.
- **The CRC is table-driven.** A bit-by-bit CRC-16 over 5 KB takes about 1 ms at 240 MHz, which would be a noticeable share of each 5 ms transaction.

### Frame format

| Offset | Size | Field    | Notes                                         |
|-------:|-----:|----------|-----------------------------------------------|
| 0      | 2    | magic    | `A5 5A` — helps catch wiring or mode errors   |
| 2      | 1    | type     | `'D'` data from server, `'A'` ack from client |
| 3      | 1    | reserved | 0                                             |
| 4      | 2    | seq      | little-endian                                 |
| 6      | 2    | len      | JSON byte count, little-endian (0 for an ack) |
| 8      | 2    | crc      | CRC-16/CCITT-FALSE over the JSON bytes        |
| 10     | 2    | reserved | 0                                             |
| 12     | len  | payload  | JSON text, not NUL-terminated                 |
| …      |      | padding  | 0–3 zero bytes, up to a multiple of 4         |

The server clocks `12 + len` rounded up to a multiple of 4. The ack is just the 12-byte header, with `len = 0` and `crc = 0xFFFF` (the CRC of an empty payload), followed by zeros for the rest of the transfer. The largest JSON that fits is `MAX_FRAME_SIZE - 12` bytes (16372 with the default setting).

## 4. Caveats and potential problems

### Board-specific (ESP32-POE-ISO)

1. **The UEXT SPI pins are also the microSD card pins.** GPIO2, GPIO14 and GPIO15 are the SD card's 1-bit SDMMC bus. **Remove the microSD card** from both boards, and don't use `SD_MMC` in this firmware.
2. **GPIO2, GPIO5 and GPIO15 are ESP32 strapping pins.** The chip samples them at reset:
   - **GPIO2 (MOSI)** must be low or floating to enter the serial bootloader. If the server is running while you flash the **client**, the server may be holding MOSI high. The upload then fails with errors such as `Wrong boot mode detected (0x13)` or `Failed to connect`. **Fix:** disconnect the MOSI jumper, or hold the server in reset, while flashing the client.
   - **GPIO15 (MISO)** low at reset turns off the ROM boot log on UART0. If the client holds MISO low while the server resets, the server's boot banner may not appear. This is harmless.
   - **GPIO5 (CS)** selects SDIO slave timing at reset. It has no effect here.
   - In general, if a board won't boot or flash, **disconnect the UEXT jumpers and try again**.
3. **Ground is required, and the ISO board makes it critical.** The "ISO" in the name means the ESP32 side is galvanically isolated from Ethernet/PoE. When both boards are powered by PoE, their ESP32 grounds share **no** common reference, so the GND jumper (pin 2) is the only shared reference. Without it, the link fails or behaves erratically. With USB power from one PC they happen to share ground through the USB cables, which can hide a missing GND wire until you switch to PoE.
4. **Don't connect 3.3 V (pin 1)** between the boards. See the ribbon-cable note above.
5. **GPIO4/GPIO36 (UEXT pins 3 and 4) are UART1.** The handshake uses GPIO4, so these pins can't also serve as a UEXT serial port. GPIO36 is input-only, so it can't be the handshake output.
6. **Ethernet is unaffected.** The LAN8720 uses GPIO12, 17, 18, 19, 21, 22, 23, 25, 26 and 27, so Ethernet can run alongside this link.

### ESP32 SPI drivers

7. **DMA alignment and size:** with DMA, the ESP-IDF drivers require word-aligned buffers and transfer lengths that are a multiple of 4 bytes. Otherwise the slave may drop or corrupt the trailing bytes. This firmware allocates buffers with `heap_caps_calloc(MALLOC_CAP_DMA)`, pads every frame to a multiple of 4, and uses a `static_assert` to check `MAX_FRAME_SIZE`. Also, both drivers default to a **4092-byte maximum transfer** with DMA, which is smaller than the 5 KB snapshot. Both boards therefore set `max_transfer_sz = MAX_FRAME_SIZE`. If you remove that, large frames fail.
8. **SPI mode with DMA:** the ESP-IDF docs note that in modes 0 and 2 with DMA, the ESP32 slave launches its MISO data half a clock early. The master then has very little hold time. Modes 1 and 3 avoid this, which is why the default is `SPI_MODE_NUM=1`. If the server sees garbage on MISO while the client receives correctly, check this first.
9. **Clock speed, and why MISO fails first:** these pins go through the GPIO matrix, not IO_MUX, which adds delay in each direction.
   - **MOSI** (server → client, the JSON): the slave samples it internally. ESP-IDF's documented ceiling for an ESP32 slave on GPIO-matrix pins is around 10 MHz, and in practice it depends on the wiring.
   - **MISO** (client → server, the ack): the slave's output delay (about 75 ns) plus the master's input delay has to fit in half a clock. For a 75 ns delay, `spi_get_freq_limit()` puts full-duplex reads at about 8.9 MHz. The server prints this limit at boot and warns if you're above it. The driver would normally refuse to set up full duplex above the limit. This firmware sets `SPI_DEVICE_NO_DUMMY` to skip that check, because the ack is small and CRC-checked. Above the limit, **expect server FAILs from corrupted acks before the client shows any FAILs.**
   - **Tuning:** step up through 8 → 10 → 13.3 → 16 → 20 MHz and watch both summaries. If only the server fails, MISO timing is the limit. If the client fails too, MOSI or SCK signal quality is the limit: shorten the wires, add a solid GND (a second GND wire helps), and put 33–100 Ω series resistors at the driver end of SCK and MOSI.
10. **The slave can't pause the master.** Without the handshake (`USE_HANDSHAKE=0`), the server clocks blindly on its timer. That only works while the client re-queues much faster than `SEND_INTERVAL_US`. Otherwise frames are lost without any error, and the client's CS log may show edges with no completed transaction.
11. **Handshake race when sending back to back:** HS drops in the client's `post_trans_cb` a few microseconds after CS rises. With `SEND_INTERVAL_US=0`, the server checks the handshake again almost immediately, so it could see the previous HIGH and clock into a slave with nothing queued. **The server avoids this** by waiting (up to 1 ms) for HS to go low after each transaction, before checking for the next HIGH. If you remove that wait, expect roughly one lost frame for every transaction.
12. **CS must toggle between transactions.** The slave uses CS going high to mark the end of a transaction. Holding CS low across several transfers merges them into one.
13. **Partial transfers:** if CS goes high early (for example, the server resets mid-frame), `trans_len` is shorter than the frame. The client reports it as truncated or with a bad CRC, and that counts as a FAIL.
14. **MISO is always driven.** The ESP32 slave doesn't reliably tri-state MISO when CS is high. That's fine for one point-to-point link, but you can't add a second slave on the same MISO line without a buffer.
15. **Reset and hot-plug:** while the server is resetting, its SCK, MOSI and CS float. The client enables internal pull-ups on those three lines so noise isn't seen as a transaction. If the client resets, the server gets a handshake timeout and skips frames until the client is back. The seq counter then shows the gap (`seq jumped` in verbose mode).

### Logging

16. **Serial output is slow compared with SPI.** In verbose mode the client prints the whole JSON for every frame (over 5 KB). At 115200 baud that takes about half a second, which is why `VERBOSE_LOG=1` needs a slow `SEND_INTERVAL_US` (1 s or more). The default summary mode prints about 45 bytes per 100 transactions, which fits easily in the UART FIFO and doesn't slow the loop.
17. **CS edge timestamps on the client** come from `micros()` in a GPIO ISR. They are accurate to a few microseconds, which is enough to see the CS low window, not for timing analysis. Use a logic analyzer for timing. The six UEXT jumpers are easy probe points.
18. **What limits throughput:** almost all of it is wire time. Each frame is (12 + JSON length) × 8 bits ÷ SCK: 5.1 ms at 8 MHz, 4.1 ms at 10 MHz, 2 ms at 20 MHz. Per-transaction overhead is about 0.2 ms: handshake turnaround, the client's CRC and 5 KB compare, and re-queuing. So raising `SPI_CLOCK_HZ` is the main lever (see caveat 9). A smaller payload is the other: for example, send only the fields that changed or a more compact format, rather than the full retained MQTT messages. The server loop busy-waits on core 1. That's fine because the ESP32 Arduino core doesn't run the task watchdog on core 1's idle task.
19. **The snapshot is fixed at build time.** Both boards compare against the same `meter_snapshot.h`. If you regenerate it and reflash only one board, every frame FAILs on the client, which reports a payload mismatch, while the server still shows OK. When live MQTT data replaces the hardcoded JSON, the client check should become just a CRC and length check, possibly plus JSON parsing.

## 5. Troubleshooting quick reference

| Symptom | Likely cause |
|---|---|
| Server: `handshake TIMEOUT` every time | Client not running, pin 3 not wired, or no GND |
| Client: `still waiting`, no CS edges | CS (pin 10) not wired, or the server isn't getting past the handshake |
| Client: CS edges logged but `bad magic` | MOSI/SCK swapped or not connected, SPI mode or clock mismatch between builds, missing GND |
| Client OK, server `bad magic` on MISO | MISO (pin 7) not connected, SPI mode 0/2 with DMA (use 1 or 3), first frame after boot |
| Occasional `CRC mismatch` | Long or loose wires, clock too high, missing GND |
| Server FAILs, client all OK | MISO timing above the limit printed at boot. Lower `SPI_CLOCK_HZ` (see caveat 9) |
| Client every frame FAIL after a snapshot refresh | Boards built from different `meter_snapshot.h`. Reflash both |
| `FATAL: spi_bus_initialize` / `spi_slave_initialize` failed | `MAX_FRAME_SIZE` too large for free DMA memory, or pins in use |
| Client won't flash while wired | GPIO2 strapping. Unplug MOSI or hold the server in reset |
| Everything fails with an SD card inserted | SD card sharing GPIO2/14/15. Remove it |
